# Demo runbook

## Before judging

1. Start the backend with the local environment file containing approved provider keys.
2. Open the dashboard and confirm the capability matrix has loaded.
3. Do not describe a provider as connected unless the header reports it.
4. Use the v2 evidence demo if network access is unreliable.

## Scenario 1 — Deposit infrastructure attribution

1. Select Load v2 evidence demo.
2. Point out the SYNTHETIC marker.
3. Show disputed amount, terminal accounting, rule-based deposit inference, reviewed collector evidence, and evidence drawer.
4. Export the result report only as a demonstration artifact. Synthetic results cannot create an operational request draft.

Expected result: an unknown deposit-like wallet is explained through its sweeps to reviewed VASP collector infrastructure.

## Scenario 2 — Multi-hop operational workflow

1. Select Load guided demo.
2. Open the graph and inspect the attributed transfer and VASP candidate.
3. Show the saved integrity receipt and challenge the candidate evidence.

Expected result: the system separates observed transfers, reviewed VASP labels, and evidence gaps.

## Scenario 3 — Cross-chain evidence boundary

1. Open the Phase 10 documentation and recorded-real fixture.
2. Show that the Wormhole fixture is RECORDED_REAL but NOT_ELIGIBLE for continuation.
3. Explain that a destination trace becomes available only after the bridge adapter supplies the exact message ID and both event records.
4. Run the cross-chain test fixture if a technical proof is requested.

Expected result: the platform refuses to turn an unproven bridge correlation into an attribution.

## Presentation rule

Always state the data mode: LIVE, RECORDED_REAL, or SYNTHETIC. A synthetic or source-only recorded fixture is never used for an operational routing recommendation.
